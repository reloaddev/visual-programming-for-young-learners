\subsection{Experimental Design}\label{subsec:experimental-design}
Two different visual programming languages were taught to a group of middle-school students to evaluate which of the visual programming languages would be effective at conveying different programming design principles to young learners.

The programming languages were compared through A/B testing by conducting a two-day workshop.
Group 1 was taught using Scratch, while group 2 was taught using Godot Orchestrator.
Both languages are incorporated into game engines by the developers, meaning that we could use game development to teach software engineering.
Students in each group were asked to build a game using the language, which incorporated the following software development concepts:

\begin{itemize}
	\item Instantiation
	\item Modularity
	\item State Management
	\item Event Handling
\end{itemize}

These concepts were chosen as they serve as ways to introduce topics commonly taught during the first year of Software engineering at university, whilst also being commonplace in game development.
This way, the students would be able to use them in their own projects, eventually increasing motivation.
The chosen concepts were more complex than basic programming concepts, like variables or loops.
This was due to the research goal, which was to investigate how different visual programming languages convey different software design principles.

Before and after the workshop, the students were asked a set of questions to determine their knowledge of software design concepts.
This was done through a survey and a multiple choice test.
Finally, we evaluated the code created by the students to see how well they applied the different programming concepts, based on whether they used a block-based (Scratch) or a flow-based visual programming language (Godot Orchestrator).

The study was conducted in cooperation with Teknologiskolen, which is an association that teaches students between six and 18 years old in programming or other technology-related topics.
Participants were recruited from Teknologiskolen's pool of students, meaning that it was likely that participants would have some programming experience.
In response to our digital invitations, three students participated in the workshop.
All participants were male and aged between 12 and 13.
The low participation left us with two groups, one group of one student working with Scratch and another group consisting of two students working with Godot Orchestrator.
Students were assigned randomly to one of the groups.

\subsection{Language Choice}\label{subsec:language-choice}

\subsubsection{Candidates}
Several visual programming languages were evaluated before the choice landed on Scratch and the plugin Orchestrator.
Unreal Blueprints was a strong candidate, as it outperforms Orchestrator on many levels, the blueprint system is integrated in many areas of the Unreal Engine.
However, the Unreal Engine was designed for 3D development, resulting in a high computational overhead.
It cannot be assumed that the average student has hardware capable of running it; it was therefore discarded.
There are also two Roblox engine plugins that enables visual programming, that enables block-based and flow-based programming.
These plugins are behind a paywall and were not chosen because of that, and that would create a barrier of entry that other options does not have.
Makecode was also considered, but was dropped for Scratch rather quickly.
Scratch and Makecode both do the block-based visual programming, but Scratch is game focused where Makecode is more focused on Micro:bit.

The two visual programming languages chosen are Scratch and the orchestrator plugin for the game engine Godot.
The reason for these candidate to be chosen was because of their similarities, both are free to use, capable to make games, and does not have big hardware requirements.
And they cover two different visual programming paradigms.
Furthermore, Orchestrator is a flow-based visual programming language with a UI similar to Unreal’s Blueprints, a proven, viable approach for game development, and Scratch remains the state of the art for teaching programming with visual scripting.

Using the criteria defined by Mannila and Raadt~\cite{mannila_objective_2006} the two languages will be compared for their ability to introduce programming to novices.

\subsubsection{Godot Orchestrator}
Godot Orchestrator is a flow-based visual scripting language designed for seamless integration into Godot's workflow.
Rather than writing code line-by-line, users connect nodes visually to represent logic flow, making program structure immediately visible.
It was built to ensure that anything implementable in GDScript or C\# is also implementable within Orchestrator itself, providing feature parity with Godot's traditional scripting languages.

\paragraph{Suitable for teaching}

In contrast to other languages like Scratch, Orchestrator was not designed as an education tool but rather as a full industry language since it is a plugin for a professional grade game engine.

Learning Orchestrator therefore requires a foundational understanding of variables, dataflow, and functions/methods, but it remains reasonably accessible for learners with these prerequisites.
The visual nature of node-based scripting reduces syntax barriers, learners focus on logic and structure rather than memorizing language conventions.

However, grasping how data flows between nodes and understanding function parameters is essential before comfortable progression.
The main drawback of Orchestrator is the same drawback which can be found in all visual scripting languages: when the code becomes complex, it can be visually cluttered.
Deeply nested logic or large state machines become harder to read and debug compared to traditional text-based code, potentially lengthening development time for intricate systems.

The user interface, while familiar and easy to use for those with experience in other flow-based languages like Unreal's Blueprints or the general Godot workflow, can be overwhelming for people unfamiliar with these tools.

\paragraph{Can be used to apply physical analogies}
Godot is a powerful engine with extensive creative possibilities.
It enables learners to create fully functional, even commercially viable games.
Its 2D and 3D capabilities, physics engine, and animation tools allow for rapid prototyping.

The ability to visually simulate real-world interactions, such as physics-based movement or object interaction, allows learners to apply programming concepts through meaningful analogies.

The amount of freedom should allow for a high amount of motivation since there is full creative freedom.

\paragraph{Offers a general framework}

As part of a full-featured game engine, Orchestrator supports a wide range of programming concepts.
For instance, Godot provides built-in support for patterns such as the observer pattern, allowing learners to explore event-driven architectures.

Furthermore, the environment enables the use of functions, classes, and other object-oriented programming constructs, supporting the development of a general and transferable understanding of software design principles.

This supports the development of transferable programming knowledge by exposing learners to concepts that extend beyond the visual environment.

\paragraph{Promotes a design driven approach for teaching software}

Orchestrator partially supports a design-driven approach by representing programs as interconnected nodes within a graphical environment.
This structure makes the flow of execution explicit and allows learners to reason about program behavior in terms of control flow and interactions between components.
In this sense, it supports thinking about problem structure rather than focusing solely on individual instructions.

Furthermore, as part of the Godot game engine, Orchestrator is embedded within a broader development environment that includes tools, libraries, and assets.
This allows learners to engage with elements of the software development process beyond simple implementation, such as prototyping and system integration.

However, Orchestrator does not explicitly enforce design principles or provide a structured methodology for software development.
The flexibility of the node-based approach allows learners to construct programs in an unstructured manner, which may result in complex or poorly organized graphs.
As such, while Orchestrator facilitates aspects of design-oriented thinking, it does not fully promote a comprehensive design-driven methodology for teaching software.

\paragraph{Is interactive and facilitates rapid code development}

Orchestrator, as a visual scripting system integrated within a game engine, enables code to be tested immediately within the game environment.
This provides instant visual feedback, allowing learners to quickly observe the effects of their changes and iterate on their solutions.
Such interactivity supports rapid prototyping and encourages experimentation.

However, the development process is inherently tied to a game or scene context.
This means that implementing and testing new ideas typically requires at least a partial setup of a larger application, rather than allowing completely isolated experimentation.
As a result, while Orchestrator provides strong interactive feedback and supports rapid development, it only partially fulfills the criterion, as it does not fully support testing small program fragments independently of a broader context.

\paragraph{Promotes writing correct programs}

Orchestrator promotes the development of correct programs through its built-in type checking and error prevention mechanisms.
It prevents invalid connections between incompatible types, reducing the likelihood of type-related bugs during development.
Additionally, functions and variables are represented as predefined nodes that are selected and placed in the graph, eliminating syntactic errors such as misspellings.

However, while these features reduce common programming mistakes, they do not provide mechanisms for systematically ensuring program correctness.
Unlike approaches such as Design by Contract, Orchestrator does not support explicit validation of program behavior through preconditions, postconditions, or invariants.
As a result, correctness is primarily achieved by preventing low-level errors rather than encouraging a fully structured and disciplined approach to software verification.
Therefore, Orchestrator partially fulfills this criterion.

\paragraph{Allows problems to be solved in ``bite-sized chunks''}

Orchestrator supports problem decomposition by allowing programs to be structured into smaller, manageable components such as functions and classes.
Functions enable specific pieces of functionality to be defined independently, allowing learners to focus on individual aspects of a problem before integrating them into a larger system.

Additionally, the Godot engine introduces a hierarchical structure through its scene-based architecture.
Each scene encapsulates a specific piece of functionality, such as a player character or an enemy, which can be developed and tested independently.
These scenes can then be composed to form more complex systems, supporting a top-down understanding of the overall application.

This combination of functional decomposition and hierarchical organization allows learners to approach problems in smaller, comprehensible steps, thereby fulfilling the criterion of enabling problems to be solved in ``bite-sized chunks''.

\paragraph{Provides a seamless development environment}


Orchestrator benefits from its integration within the Godot game engine, providing a unified environment for scripting, asset management, and testing.
Learners can write, test, and debug code within the same interface, reducing the need to switch between tools and supporting a smooth development workflow.
This integration simplifies the development process and allows learners to focus on problem-solving rather than tool configuration.

\paragraph{Has a supportive user community}


Godot has an active and growing open-source community that provides extensive documentation, tutorials, and discussion forums.
While the Orchestrator plugin itself has a smaller and less mature community, learners can still benefit from the broader Godot ecosystem, as many concepts and workflows are shared across scripting approaches.

\paragraph{Is open source, so anyone can contribute to its development}

Godot is simple to set up: a single executable with no installation required, and it is free and open-source.
Orchestrator is installed as a plugin via the asset manager and is also open source.

\paragraph{Is consistently supported across environments}

Godot the engine that Orchestrator is a plugin for is available on a variety of platforms and therefore orchestrator is also available on all platforms.

\paragraph{Is freely and easily available}

Godot is a free game engine, and the plugin orchestrator is easy to install from within the engine.

\paragraph{Is supported with good teaching material}

Godot receives regular updates (version 4.6.2 at the time of writing), and has an array of teaching materials specific to the engine.
However, Orchestrator is newer and has a less mature ecosystem than tools like Unreal’s Blueprints, resulting in fewer tutorials.
It shares built-in functionality with Godot’s textual scripting language, allowing many existing tutorials to be reused.

\paragraph{Not only used in education}

It is not primarily designed for education, but rather for professional game development.
However, its features make it suitable for educational use in certain contexts.

\paragraph{Is extensible}

Orchestrator seamlessly integrates with any library meant to run with the other languages of the Godot engine.
Any class written in the other languages can be referenced in the visual script.

\paragraph{Is reliable and efficient}

The execution of code is generally efficient, as it builds upon the optimized core of the Godot engine, which is implemented in C++.
However, visual scripting may introduce some overhead compared to lower-level implementations.

\paragraph{Not an example of the QWERTY phenomenon}

It is not an example of the QWERTY phenomenon, it is a relatively new language within a relatively new game engine, the engine is forward-looking and so far the language is as well.

\paragraph{Concept Coverage}
As a language designed for a full game engine, Orchestrator can implement all the concepts we plan to teach in this workshop, though some may be moderately complex to use.

Instantiation – Creating and spawning game objects dynamically within scenes

Orchestrator handles instantiation through dedicated nodes that load and create scene instances at runtime.
Learners connect an ``Instantiate Scene'' node, specify the scene path, optionally pass constructor parameters through input pins, and receive the instantiated object as output.

This could teach what instantiation is but how is still abstracted away.

This node-based approach makes the creation process explicit and visual, learners see exactly what's being created and what data flows into it.
The drawback is that complex object pooling or batched instantiation patterns become verbose when represented as node chains.

Functions – Organizing reusable logic into callable blocks

Orchestrator treats functions as first-class node graphs.
Learners create custom event/function nodes, define input parameters as visual pins on the left side and return values on the right side, then build the function logic by connecting nodes within that graph.

This visual representation makes the relationship between inputs, logic, and outputs immediately clear.
However, overloading (multiple functions with the same name but different parameters) isn't natively supported, and complex recursive functions become difficult to visualize.

State Management – Tracking and updating object properties

Orchestrator manages state through member variables (properties) that persist on the script node.
Learners define these variables and use \texttt{Set Property} and \texttt{Get Property} nodes to modify and read them.

Orchestrator supports a wide range of data types, including primitives, vectors, and complex structures such as arrays and dictionaries, allowing learners to work with a variety of data representations.

State changes are explicit, which makes tracking easier.
The downside is that this explicitness can create sprawling node graphs when many variables are used.

Can be used to create state machine easily by making use of booleans just like normal textual languages.

Event Handling – Responding to input, collisions, and signals

Orchestrator connects to Godot's signal system through event nodes.
When a signal is emitted (input, collision, or custom event), a corresponding node fires.

Learners connect input nodes (e.g., \texttt{Input Action Pressed}) directly to logic, making cause-and-effect relationships clear.
However, managing multiple overlapping events can lead to tangled graphs.

\subsection{Surveys}\label{subsec:surveys}
The study included both a pre- and a post-survey to determine the students’ assessment of their programming abilities.
The pre-survey was carried out before the workshop to determine the students’ experience with programming and software design principles.
Using a Likert scale students could indicate whether they agree or disagree with statements like “I have a lot of experience in writing computer programs”, “I have a lot of experience with visual programming languages (e.g., Scratch)”, or “I can confidently explain how events handling can be implemented in computer games”.
Note the focus on computer games in the last example.
Because we used computer games to teach software design principles, we decided to go for more games-related statements instead of generic programming-related statements.
We deem this approach defendable, as game development has served as proxy for teaching programming principles in other research projects\cite{mathrani_playit_2016,papadakis_evaluating_2020}.


A corresponding post-survey, with primarily the same questions, was performed after the workshop.
Its goal was to capture the workshop's effect on self-assessing their software design skills.
Concretely, it was used to identify differences between Scratch and Godot Orchestrator teaching software design principles.
Compared to the pre-survey, the post-survey was enriched by additional statements, to receive feedback on the usability of both tools.
Those statements were phrased like “The visual programming language helped me to understand how my game saves and updates data”.
Similarly to the pre-survey, statements were mapped to the software design concepts we wanted to convey during our workshop, as defined in the previous section.
The surveys were conducted anonymously, however it was ensured that pre- and post-survey answers could be mapped to the same identifier.
As recommend in\cite{nemoto_developing_2013}, other data collection methods (multiple-choice test, artifact evaluation) have been added, to get a more complete picture of the research subject.


The question for both surveys were designed with students in mind, which would have at least a basic understanding of programming and related concepts like variables and control structures.
According to the project focus on young learners, we expected to teach either middle school or young high school students.
Thus, one challenge was to find a tone and wording that would be understandable, yet meaningful enough to describe concepts like modularity or instantiation.
A survey statement regarding modularity was phrased like this: “I can confidently explain, how a game can be split into several parts”.
While it does not mention the concept of modularity explicitly, it still conveys a similar idea using simpler language.
Other statements used the concept’s name, if we deemed it understandable enough: “I can confidently explain, how programs react to events”.
As Berends~\cite{berends_survey_2006} stresses, creating questions that address the actual research goal is essential.
Therefore, we tried to focus the survey questions on the student’s understanding of the earlier presented software design principles.
To achieve comparability, we included those questions both in pre- and post-survey.
Apart from asking about the software design principles, pre- and post-survey differed in the remaining question.
Whereas the pre-survey collected data regarding the student’s programming experience, the post-survey included more general questions regarding usability of the respective visual programming languages.

\subsection{Educational Workshop}\label{subsec:educational-workshop}
The workshop started with us explaining the above concepts and introducing the language the group would be using.
Therefore, a 45-minute-long lecture was held, where students were involved by asking them questions and letting them ask questions.
Afterward, the students received a quick introduction into their respective game engine.
The students would then take on the role of software engineers in a game development team.
As part of the teaching materials, students were given a game design document and pre-prepared assets placed in the game.
They also received a description of the functionality their code was expected to implement.
As instructors, we stood by to help the students in case they got stuck.
This way, the students would be able to focus all their attention on writing the code, rather than understanding every aspect of the engine.
This design was chosen to account for the limited amount of available time, whilst maximizing the focus on software engineering.
The main downside of this method is that it does not emphasize creativity.
Following instructions is definitely less creative than turning your own idea into a video game.

The game is a simple shooter, in which the player is being chased by an ever-increasing amount of ghosts.
The player can shoot the ghosts to gain points, but the game will end if a ghost hits the player.
Further, the player can avoid the ghosts by moving left and right, or by jumping over them.
The goal is to gain as many points as possible before being hit by a ghost.

The software design concepts, that we wanted to investigate, were mapped to different features of the game to be built.
Animations for the gun are handled using a state machine (state management).
Each ghost is an instance, which makes it possible for them to spawn continuously during runtime for as long as the game goes on (instantiation).
Functions are used to organize the code and make it reusable without having to write the same lines multiple times (modularity).
Based on our testing with visual languages, we determined this to be even more important in these languages than in text-based ones.
Visual code easily covers the screen and becomes unmanageable, so organizing code into functions is crucial to be able to read it.
Both game engines allow usage of events to enable communication between scripts, so it makes sense to teach that as well.
In our game events were for example used to let ghosts know if they were hit by a bullet or to react to the player’s key input (event handling).
Hence, all the earlier mentioned software design concepts could be found in our game.
The instructions, that came with the game design document and that students were encouraged to follow, tried to expose the students to problems, which could be solved by using one of the concepts.
However, the students were not obliged to use these concepts.

The project phase of the workshop was split into four blocks of around 90 minutes each.
The four blocks were distributed to two different days, as the workshop was held over two days.
On each day, we had a 30 minute-break between each block.
As Ramstetter et al.\cite{ramstetter_crucial_2010} summarizes, breaks help the children to re-gain their focus and attention.
Further, we gave them access to a whiteboard to write down their thoughts, for example when they could not instantly figure how to solve a problem with code.
To collect additional qualitative data, we took notes throughout the workshop to capture student behavior and feedback when working with the chosen visual programming languages.

In both cases the questions were the same to achieve comparability.

The other questions were designed in a similar way, while addressing other programming concepts too.

\begin{enumerate}
	\item You are making a game with 5 enemy types, which all move in the same way.
	      What is the best way to structure your game?
	      \begin{enumerate}[label=\Alph*.]
		      \item Copy the same movement-logic into every enemy.
		      \item Make one shared enemy behavior and use it for all enemies.
		      \item Place all enemy logic into a very large code block.
		      \item I don't know.
	      \end{enumerate}
	      \textbf{Correct answer: B}
\end{enumerate}

The overall idea was to create questions that would strike an appropriate difficulty, while also mapping to the concepts we wanted to convey: modularity, instantiation, state management and event handling.
While the questions were the same for both tests, their order was randomized between both trials.
Having the same questions for both would allow for easy comparability.
With the help of the questions we wanted to see to what extent the visual programming languages would help improve the student’s understanding of the different concepts.

\subsection{Artifact Evaluation}\label{subsec:artifact-evaluation2}
Along with surveys and multiple choice test we wanted to also evaluate the student-created artifacts (i.e.\ the game).
As surveys and tests come with their own limitations, we wanted to add more data measures to get a more complete picture of the students’ learnings throughout the workshop.
This method has been used in other studies concerned with teaching programming concepts, like~\cite{grover_assessing_2014}.

In order to analyze the student projects in a structured way, we created an evaluation rubric upfront.
Again, we focused on the four concepts we wanted to convey to the students: modularity, instantiation, state management, event handling.
For each of them we tried to come up with different levels of “goodness”, i.e.\ how well the students made use of each of the concepts in their projects.

Modularity was deemed the most straightforward concept out of the four.
Generally, it is a rather widely defined concept which can appear in different forms.
For our project, we mainly considered variables and functions (custom blocks in Scratch) as signals of modularity.
For our evaluation we consider both frequency and quality of usage.
Accordingly, a “good” student will use modularity correctly whenever it makes sense.
Features where we expected heavy use of functions and variables were player movement and enemy behavior.

Instantiation is an important concept both in programming in general and specifically in game development.
The features defined in our game design document made use of instantiation likely to be used to create enemies and projectiles, as those are created in great numbers.
Again, a “good” student will use instantiation with confidence, whenever it is appropriate.
Moreover, they might even create a central “factory” to create new instances of an object.
Finally, we would like to see students using the same instantiation mechanism to create different variants of an object, e.g.\ different variants of ghosts.

State management is similar to modularity a rather wide concept, that can mean different things.
In our case, we want to focus on conveying the idea of state machines or the related state pattern \cite{} [cite GoF, Design Patterns].
We expect this to be the hardest concept for the students to grasp.
Therefore, it is only expected to be used for modeling the weapon’s different states like ready and reloading.
It might be useful with other game features too, however we deem everything that goes beyond to be exceptional.
For a state machine to be implemented, we expect clear definition of states and transitions, that check for whether the current state is compatible with the next state.

Event handling is a concept that can be hard to implement from scratch.
However, both Scratch and Godot Orchestrator provide event handling out-of-the-box.
Thus, students can focus on using those existing mechanisms in their respective projects.
It is important to mention here, that Scratch’s main way of making different components communicate is events (signals).
There is no way for one component to invoke another.
This is different in Godot, which might lead to more non-event-based communication.
To see event handling effectively implemented, we would like to see that one component listens for events that another component emits.
In the best case, we would see students use events to decouple components from each other.

To evaluate each software design principle, we came up with the following scales:
\begin{itemize}
	\item Frequency: Always, Usually, Often, Sometimes, Never
	\item Quality: Appropriate, Somewhat Appropriate, Inappropriate
\end{itemize}
