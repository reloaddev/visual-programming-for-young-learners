\subsection{Software Engineering in Education}

\subsubsection{Programming Education}\label{subsub:programming-edu}
Though programming is not the main focus of software engineering it serves as the entry point, where students learn fundamental concepts that later extend into more advanced topics such as software design and system architecture.

Because programming serves as the entry point to software engineering, the choice of programming language is important, as languages with a steep learning curve may discourage beginners from engaging with the field~\cite{resnick_scratch_2009}.

The specific language to use for this entry point has been a history of debate~\cite{villagomez-palacios_bridging_2025}, as language preference is subject to personal preference and efficiency varies between learners.
Because these preferences are subjective, it is often difficult to objectively compare programming languages and their suitability for teaching.
This is something that Mannila and Raadt have sought to rectify in their paper \textit{ "An Objective Comparison of Languages for Teaching Introductory Programming"}\cite{mannila_objective_2006}, wherein they compare different programming languages to find the one which is the best for teaching beginners.
They have collected 17 different criteria drawn from the design decisions made by creators of languages that are considered ``teaching languages''.
These criteria are used as a methodology to evaluate the suitability of programming languages for teaching.
More importantly, the language should enable students to focus on fundamental programming concepts, rather than being hindered by syntactic complexity~\cite{villagomez-palacios_bridging_2025, mannila_objective_2006}.
Their work also highlights that introductory programming languages should support problem decomposition, modular thinking, and gradual progression from simple to more complex constructs.

One of the problems in teaching software engineering through programming is the so-called “double burden”, where learners are required to simultaneously understand problem-solving logic and the syntax of a programming language.
This combination introduces a significant cognitive load, particularly for beginners, who may struggle to express simple ideas in syntactically correct programs~\cite{villagomez-palacios_bridging_2025}.

A key goal of introductory programming education is therefore not mastery of a specific language, but the development of transferable problem-solving skills and an understanding of core programming concepts.

One approach to introducing these concepts while avoiding the “double burden” associated with traditional textual programming is the use of visual programming environments, which allow learners to focus on logic and structure rather than syntactic details.
Consequently, a variety of visual programming languages have been developed, each offering different approaches to representing program structure and execution.

\subsection{Visual Programming Languages}

\subsubsection{Logo}
One of the first steps towards visual programming languages was Logo, which was developed as a programming language for children\cite{papert_mindstorms_1980}.
The general idea of the language is to put children into a position, where they are not just being taught how to use a language, but where they can explore the world of programming.
For instance, it might help children to understand that programming is not really about getting it right or wrong the first time, but to iteratively improve a program over time by running and debugging it.
Logo makes use of turtle graphics to make it appealing to children.
One of the initial tasks is to write a program that moves a turtle on the screen.
Children can reflect on their thinking process by imagining the steps they would take if they were the turtle, and thus understand how a computer program consists of different steps or instructions.
Logo is considered one of the first attempts to make programming accessible to children.
Still, it is not a visual, but a textual programming language.

\subsubsection{Scratch}
In 2007, Resnick et al. launched their visual programming language Scratch\cite{resnick_scratch_2009}.
Compared to the previously presented language, Scratch does not rely on textual code snippets, but graphical programming blocks.
Each block serves a purpose, e.g., hold a variable or check for a condition, and can be combined with other compatible blocks.
This allows learners to try out many things, while being protected from syntax errors common in textual programming.
Scratch is highly interactive, thus promoting learners to explore solutions and iteratively create their programs.
Further, the programming environment allows for a high degree of personalization to motivate learners.
Scratch projects can be shared with others, thus allowing new projects to re-use code from existing projects.
The concept of re-use plays an important role in other programming languages too, where projects rely on libraries or frameworks to avoid having to program every functionality from scratch.

\subsubsection{Snap!}
While Scratch being pointed at children's education, `Snap!' attempts to recycle Scratch’s core ideas and make it viable for non-major computer science education\cite{harvey_bringing_2010}.
It was initially developed as an extension to Scratch, which introduced functions to make use of recursion and the possibility to create lists of lists, enabling the construction of other data structures.
In addition, Snap! can serve object-oriented programming allowing for the creation of class-like constructs and their instantiation as objects.
Even inheritance becomes possible with Snap! The creators of Snap! wanted to avoid having separate languages for children and more mature learners, as this would split the community into two parts, where learners had to switch from one to another language.
Instead, they advocate for an approach where switching from Scratch to Snap! feels more like enabling some additional features to make the language more powerful.

\subsubsection{MIT App Inventor}
While other visual programming languages attempt to teach programming through animation or game development, MIT App Inventor utilizes mobile app development as a teaching medium~\cite{patton_mit_2019}.
Prebuilt visual elements (e.g.\ buttons, text elements) can be dragged into an app, making it easy to the implement the app interface.
Further, code blocks as in Scratch or Snap! can be used to implement more complex behavior.
Similar to other visual programming languages, App Inventor's target group is users that have not graduated from a computer science program.
The focus lies on iteration and rapid prototyping.
Also, App Inventor provides a WYSIWYG (What You See is What You Get) output window, which shows users how changing code affects the output app.
A companion app, that users can install on their mobile phone, allows users to test their app on real devices.

\subsubsection{Visual Programming Paradigms}
Visual programming languages can be categorized into different paradigms depending on how they represent a program's build-up and execution.
Early kinds of visual programming languages describe different styles of representation, this includes flowchart and block-based approaches~\cite{myers_taxonomies_1990}.

Block-based visual programming represents its programs using graphical blocks that match programming constructs like loops, conditionals and expressions.
The blocks are designed to join together in ways that are syntactically correct, they support this by having the block's shape tell the user where they can be connected to another piece.
Scratch is a block-based programming environment, meant to support early programming learning with its graphical programming elements~\cite{resnick_scratch_2009}.

Node-based visual programming is often linked with dataflow systems, here the program is graphically represented as a graph that is connection to nodes.
These nodes represent a program's operations, and the node's connections to other nodes represents the flow of data and their execution.
Unreal Engine's blueprints\cite{epicgames_blueprints_2025} and Godot Orchestrator\cite{godot_orchestrator} which is a plugin for the Godot game engine, both use similar visual node based programming to interact with their game engines.

These paradigms are different approaches to visual programming, they share the common trait of using graphical elements to represent programming constructs, they differ in their visual representation and their use cases.

\subsection{Visual Programming or textual programming Languages in Education}

With both visual and textual programming being introduced this raises the question of which approach is more effective for introductory programming education and the development of underlying conceptual understanding.

As mentioned in~\ref{subsub:programming-edu}, one of the primary challenges in introductory programming is the “double burden” faced by novices, who must simultaneously learn problem-solving logic and the syntax of a programming language.
Visual programming environments have been proposed as a solution to this issue, enabling a “logic-first, syntax-second” approach, where learners can focus on computational thinking before dealing with syntactic complexity.

However, research comparing visual and textual programming languages suggests that there is no clear consensus on which approach is superior.
A systematic literature review by Noone and Mooney~\cite{noone_visual_2018} highlights that while visual programming languages can improve accessibility, engagement, and early conceptual understanding, but when times come for more complex topics it has a tendency to fall short.
The widespread availability of visual programming environments, both online and as free downloadable tools, helps mitigate some of their limitations.
These environments can serve as an effective introduction to programming concepts, particularly when followed by a structured transition to textual languages, for example through side-by-side comparisons.
Additionally, their accessibility and interactive nature can increase motivation and improve retention, especially among younger learners~\cite{noone_visual_2018}.

Similarly, Fernandes et al.~\cite{fernandes_blocks_2026} found that both block-based and text-based paradigms significantly improve students' conceptual understanding, but differ in how learners approach programming tasks.
While visual programming has often been theorized to be easier to use and less error-prone due to reduced syntactic complexity, empirical evidence does not always support this assumption.

Furthermore, Fernandes et al.~\cite{fernandes_blocks_2026} conclude that both block-based and text-based programming environments have potential in teaching computational thinking, with neither approach being inherently superior.
Instead, each paradigm appears to support different conceptual areas more effectively.
For example, sequences are more clearly understood in text-based environments, whereas procedures are more effectively learned in block-based environments.

While previous research has demonstrated the benefits of visual programming languages and computational thinking in introductory programming education, there exists limited work directly comparing different visual paradigms in the context of teaching software design concepts.
In particular, the distinction between block-based and node-based or node-based programming approaches has received relatively little attention.

This study aims to address this gap by examining how different visual programming paradigms support the learning of key software engineering concepts, including modularity, instantiation, state management, and event handling.
