We have compared two visual programming languages in regards to their ability
to convey software design principles (modularity, instantiation, state management,
event handling) to young learners. On a higher level, we have analyzed how two
different visual programming paradigms, block-based (Scratch) and flow-based
(Godot Orchestrator), emphasize different software design concepts. The study
was conducted as an educational workshop, where two student groups were taught
different programming principles using either or the other language. Data was
collected using surveys, multiple-choice tests, student observation and
evaluation of their created code.

Our results show that Scratch generally correlated with a better understanding
of different software design principles than Godot Orchestrator. Scratch led to
a good understanding of modularity based on survey, multiple choice test and
artifact evaluation. On the other hand, the concept of instantiation was not
well conveyed in Godot Orchestrator. Both languages seem to be viable to teach
some of the selected software design princples, though. Scratch appears easier
to use than Godot Orchestrator, as it comes with a simpler user interface, more
abstraction of difficult concepts and less "building blocks".

The study was also an attempt to compare an educational visual programming language
(Scratch) to a more industry-relevant language (Godot Orchestrator), to see how
they emphasize different software design princples. Our results point towards that
language choice might be less important than expected. Instead, our observations
indicate that it might be more important to find a familiar language when
attempting to teach software design to young learners. Teaching both fundamentals
and software design at the same time can lead to confusion, independently of
which language is used for teaching.

When starting from zero, Scratch might be the better choice as it abstracts from
low level details (e.g., vectors) that might not be needed initially. This is
especially useful when teaching more straightforward principles like modularity,
however it can also be limiting when implementing more complex concepts like
finite state machines. Godot yields more possibilities if students already have
strong programming foundations, as it yields more building blocks, customizability
and optimization. Thus, it can be used to implement more difficult software
patterns elegantly too. Overall, it remains essential to introduce any language
proporly, if students have not used it before.

Similar to our study, future research should consider using other visual
programming languages for teaching software design. While we relied on Godot
and its community-backed plugin Orchestrator, it would be interesting to see
how an industry-grade language like Unreal Engine's Blueprint \cite{epicgames_blueprints_2025}
system could support student learning. We did not use it in our study due to
limited computing resources. Alternatively, it might be promising to compare
two educational languages (e.g., Scratch, Greenfoot) that represent different
visual programming paradigms. \cite{utting_alice_2010} discusses and compares
different visual programming languages and their suitability for teaching, but
does not include any teaching activity with students.

Lastly, it remains essential to compare visual and textual programming languages.
\cite{fernandes_blocks_2026} conduct such a study and find that both paradigms
come with their own strengths. However, they do not consider artificial intelligence,
which is now widely available and might support students with learning one or
the other paradigm better. There might be new ways of using textual programming or visual
programming languages to teach programming concepts, if every student has an
individual AI tutor. Related litererature is still spread thin, which is why we expect
a lot of interesting research opportunities in that area. As AI is increasingly used
in the industry, educators should at least consider where and where not its use
would improve student learning.
